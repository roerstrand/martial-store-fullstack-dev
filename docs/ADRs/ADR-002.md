# ADR-002: Lagerindelning controller → service → repository i servern

- **Status:** Accepterad
- **Beslutsdatum:** 2026-05-12
- **Dokumenterad:** 2026-11-15 (i efterhand, se [README](README.md))
- **Underlag i historiken:** `2d49723` (ProductService och asyncHandler i controller), `ed82331` (Repository), `b2f6d3d` (userRepo och userService)

## Kontext

API:t hanterar produkter, användare, artiklar, kundvagn, ordrar och favoriter. Varje domän har HTTP-hantering, affärsregler (t.ex. lösenordshashning, lagerkontroll, ordertotaler) och databasanrop. Om allt hamnar i route-hanterarna blir de svåra att testa och att ändra var för sig.

## Alternativ

**A. Logiken direkt i routes/controllers**
- Fördelar: minst kod och snabbast att komma igång.
- Nackdelar: HTTP, affärsregler och Mongoose-anrop blandas, och logiken går inte att återanvända eller testa utan HTTP.

**B. Controller → service (två lager)**
- Fördelar: affärsreglerna skiljs från HTTP.
- Nackdelar: services anropar Mongoose direkt, så varje databasändring påverkar affärslogiken.

**C. Controller → service → repository (valt)**
- Fördelar: tydligt ansvar per lager (controller hanterar HTTP och statuskoder, service affärsregler, repository databasåtkomst), och varje domän kan lyftas ut eller ändras utan att påverka de andra.
- Nackdelar: fler filer per domän, och tunna lager för enkla CRUD-flöden.

## Beslut

Alternativ C. Varje domän har en fil per lager: `controllers/`, `services/` och `repositories/`. Controllers använder `express-async-handler`, och fel samlas i `middleware/errorMiddleware.js`.

## Konsekvenser

- Nya domäner följer samma mönster: först cart, sedan order och favorite (2026-05-26).
- Services kan testas med mockade repositories.
- Byte av datalager påverkar bara `repositories/`.
