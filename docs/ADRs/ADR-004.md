# ADR-004: Inloggning med JWT i httpOnly-cookie och CSRF-header

- **Status:** Accepterad (ersätter den ursprungliga lösningen med token i localStorage)
- **Beslutsdatum:** 2026-05-13 (JWT), 2026-11-13 (flytt till httpOnly-cookie)
- **Dokumenterad:** 2026-11-15 (i efterhand, se [README](README.md))
- **Underlag i historiken:** `b294351` (bcrypt-hashning), `acfb964` (validateTokenHandler), `306dbb6` (httpOnly-cookie, logout och CSRF-header), `ecf50e2` (klienten använder cookie i stället för localStorage)

## Kontext

Kunder ska kunna logga in för att se ordrar, favoriter och adresser, och admin ska kunna hantera produkter och ordrar. API:t är tillståndslöst och ska kunna köras på en annan domän än klienten (se ADR-006). Först sparades token i `localStorage`, och då kan den läsas av all JavaScript på sidan, även vid XSS.

## Alternativ

**A. JWT i localStorage, skickad i `Authorization`-headern (den ursprungliga lösningen)**
- Fördelar: enkelt, och inget CSRF-skydd behövs.
- Nackdelar: token kan läsas av skript vid XSS, och klienten måste själv hantera token.

**B. JWT i httpOnly-cookie och krav på en CSRF-header (valt 2026-11-13)**
- Fördelar: skript kan inte läsa token, servern förblir tillståndslös, och CSRF stoppas av att alla skrivande anrop kräver `X-Requested-With`, som en annan sajt inte kan sätta utan CORS-godkännande.
- Nackdelar: kräver `credentials: true` och rätt `sameSite`/`secure` mellan domäner, och logout måste gå via servern.

**C. Sessioner på servern (express-session med sessionslagring)**
- Fördelar: sessioner kan återkallas direkt.
- Nackdelar: tillstånd på servern och en lagring för sessionerna, vilket ger mer drift för ett litet projekt.

## Beslut

Alternativ B. Lösenord hashas med bcrypt. Vid inloggning sätts en JWT i en httpOnly-cookie (`config/authCookie.js`). `middleware/validateTokenHandler.js` läser cookien, `adminValidator.js` skyddar admin-routes, och `csrfMiddleware.js` kräver headern på alla anrop som inte är GET, HEAD eller OPTIONS.

## Konsekvenser

- Klienten vet vem som är inloggad via `/api/users/current` vid sidladdning, eftersom den inte kan läsa token.
- I produktion är cookien `secure` och `sameSite: none` för att fungera mellan Vercel och Render.
- En token kan inte återkallas före utgång (ett dygn). Det accepteras för projektets omfattning.
