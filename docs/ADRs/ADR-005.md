# ADR-005: Klientstate via React Context och `useFetch` med service-funktioner

- **Status:** Accepterad
- **Beslutsdatum:** 2026-05-18
- **Dokumenterad:** 2026-11-15 (i efterhand, se [README](README.md))
- **Underlag i historiken:** `5d7104a` (authService, apiService och productService i klienten), `1ee9c67` (useFetch tar emot service-funktioner), `cdb1df0` (AuthContext och useAuth), `a5b051d` (FavoriteContext och CartContext)

## Kontext

Inloggad användare, kundvagn och favoriter behövs på många ställen samtidigt: navbar, produktkort, kundvagn och checkout. Övrig data (produkter, artiklar, ordrar) hämtas per sida. API-anrop ska inte skrivas direkt i komponenterna.

## Alternativ

**A. Prop drilling från `App`**
- Fördelar: inga extra beroenden.
- Nackdelar: state måste skickas genom många nivåer, och komponenter blir beroende av sina föräldrar.

**B. Redux Toolkit eller Zustand**
- Fördelar: förutsägbar global store, devtools, och skalar till stora appar.
- Nackdelar: extra beroende och mer kod än den här mängden delat state kräver.

**C. React Context för delat state, `useFetch` för sidans data, och services för API-anropen (valt)**
- Fördelar: inbyggt i React, en context per ansvar (Auth, Cart, Favorite) som kan ändras var för sig, och komponenterna anropar aldrig axios direkt.
- Nackdelar: alla som använder en context renderas om när den ändras, och utan cache hämtas datan om vid varje sidbesök.

## Beslut

Alternativ C. `AuthContext`, `CartContext` och `FavoriteContext` omsluter appen i `main.jsx`. Varje API-domän har en fil i `client/src/services/` som använder den gemensamma axios-instansen i `services/api.js`. `hooks/useFetch.jsx` tar emot en service-funktion och returnerar `data`, `loading` och `error`.

## Konsekvenser

- En ny domän kräver en ny service-fil och vid behov en egen context, utan att befintliga påverkas.
- Kontexterna kan testas var för sig med mockade services.
- Om sidorna blir många eller datamängden stor är TanStack Query ett naturligt nästa steg för cache.
